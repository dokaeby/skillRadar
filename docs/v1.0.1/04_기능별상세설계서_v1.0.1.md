## FR-001 GitHub 저장소 검색

- **입력**: `queries.yaml`의 플랫폼별 쿼리 문자열 목록
- **처리**: 각 쿼리를 `GET /search/repositories?q=...&sort=stars&order=desc&per_page=30`로 호출
- **출력**: `RepoHit` 리스트 (full_name, html_url, description, stars, language, topics, archived, fork, license)
- **license**: 검색 응답 `license.spdx_id`를 그대로 사용 (추가 API 호출 없음, 없으면 null)
- **예외**: 쿼리 결과 없음/실패 → 빈 리스트 반환, 수집 계속. 403/429/5xx는 지수 backoff + `Retry-After` 우선
- **검증**: `archived:true`, `fork:true` 항목은 클라이언트에서 제외하고 `dedupe_filter` 노드에서도 재확인

## FR-002 쿼리 설정 분리

- `src/backend/queries.yaml`에 플랫폼별 쿼리 리스트. 기본값:
  - claude: `topic:claude-skills`, `topic:claude-code-plugin`, `"claude skill" in:name,description,readme`
  - chatgpt: `topic:chatgpt-plugin`, `topic:custom-gpt`, `"chatgpt plugin" in:name,description`
  - gemini: `topic:gemini-extension`, `topic:gemini-cli-extension`, `"gemini extension" in:name,description`
- 모두 `archived:false fork:false` 조건 포함
- `Settings.queries_path`로 경로 변경 가능, `platform_queries()`가 YAML을 파싱

## FR-003 중복 제거 및 Top 10 컷

- `full_name` 기준 병합, 동일 repo는 더 높은 star 값 유지 (collect 노드)
- `dedupe_filter` 노드: archived/fork 제외 → star 내림차순 상위 10개(`_TOP_K`)만 유지
- 이후 classify/summarize/verify는 이 Top10에만 LLM을 호출해 비용을 제한

## FR-004 README 수집

- `GET /repos/{full_name}/readme?raw=1` (`follow_redirects=True`) → 앞 3000자
- 실패 시 `GET /repos/{full_name}/readme` JSON의 base64 `content` 디코딩 폴백
- 최종 실패 시 빈 문자열 (수집 중단 없음)
- sanitize 노드에서 `sanitize_readme`로 인젝션 의심 문구 라인 제거 후 `RepoClean.sanitized_readme`에 저장

## FR-005 LLM 3줄 요약

- **입력**: description + sanitize된 README
- **프롬프트 규칙**: JSON만 출력, 언어별 정확히 3줄, 영문 줄당 120자 이내,
  (1) 무엇을 하는지 (2) 사용법/핵심 기능 (3) 대상 사용자/특징 순서,
  MCP·plugin 등 기술 용어 원문 유지, 홍보 문구 금지
- **출력 스키마**: `LLMSummary` Pydantic — `summary_en`/`summary_zh`/`summary_ko` 각 정확히 3줄 강제
- **캐시**: `content_hash = sha256(description + "\n---\n" + readme[:3000])`.
  `collector._find_cached_summary`로 동일 repo+동일 hash의 이전 항목 요약 재사용 (파이프라인 `summary_cache` 콜백 경유)
- **재시도**: HTTP 오류·JSON 파싱 실패·형식 오류 시 최대 3회 시도. ko에 한글이 없으면 en을 Google 번역으로 생성
- **폴백**: 최종 실패 시 description 원문(없으면 repo명) 3줄 + ko는 Google→MyMemory 번역, `summary_status='failed'`

## FR-006 taxonomy 분류 (v1.0.1)

- **노드**: `graph/nodes.classify` → `llm_tasks.classify_repo`
- **입력**: description(500자) + sanitize된 README 2000자 + name + topics
- **출력**: `Classification(label, confidence)` — 라벨은 `TAXONOMY_LABELS` 8종
  (`agents|mcp|skills|plugins|devtools|automation|data|other`), confidence 0.0~1.0 클램프
- **모델**: `judge_model`(`LLM_JUDGE_MODEL`, 비우면 `LLM_MODEL`) — 생성 모델과 분리
- **실패 처리**: API/파싱 실패·무효 라벨 → `('other', 0.0)`. `llm_enabled=False`면 전부 other/0.0
- **저장**: `snapshot_items.taxonomy`, `taxonomy_confidence`

## FR-007 요약 검증 (verify) (v1.0.1)

- **노드**: `graph/nodes.verify` → `llm_tasks.verify_summary`
- **판정**: 요약 각 줄의 사실 주장이 README에 근거하는지 `{"supported": bool}`로 검증
- **재시도**: 불합격 시 재요약 최대 2회(`_MAX_RETRIES`), 그래도 실패 시 `summary_status='unverified'`
- **fail-open**: 검증 API/파싱 실패는 True 반환 — 검증기 장애가 수집을 막지 않음

## FR-008 랭킹 점수 (rank) (v1.0.1)

- **수식**: `rank_score = round(log10(stars+1)*20 + (summary.status=='ok' ? 5 : 0) + confidence*5, 2)`
- rank_score 내림차순 정렬 후 상위 10개(`_FINAL_TOP_N`)를 `state.ranked`에 저장
- `snapshot_items.rank_score`에 저장, `/api/topic-repos` 정렬에 사용

## FR-009 관련 주제 (related) (v1.0.1)

- **노드**: `graph/nodes.related` — LLM 호출 없음
- 같은 스냅샷 내 repo 토픽 교집합으로 공기반 점수 계산, 주제당 상위 5개 `RelatedTopic`
- `GET /api/related-topics`는 최근 30일 수집분 기준으로 동일 로직을 DB에서 계산(상위 10개)

## FR-010 오늘 증가 star 계산

- 수집일 이전의 가장 최근 스냅샷에서 `repo_full_name → stars` 맵 작성
- `stars_today = max(0, 현재 stars - 이전 stars)`; 이전 데이터 없으면 `NULL`

## FR-011 멱등 재수집

- 동일 `(platform, collected_date)` 스냅샷 존재 시 항목 cascade 삭제 후 재생성
- `POST /api/admin/refresh`, Vercel Cron, APScheduler, `cli_collect`가 모두 같은 `run_daily_collect`/`collect_all` 경로 사용

## FR-012 일일 스케줄

- APScheduler `CronTrigger(hour=SCHEDULE_HOUR, minute=0, timezone=SCHEDULE_TIMEZONE)`
- 기본 KST 06:00, `misfire_grace_time=3600`
- 앱 lifespan에서 시작, 종료 시 shutdown (로컬/상시 서버용)
- Vercel serverless에서는 `vercel.json` Cron이 `/api/admin/refresh`를 매일 호출 (UTC 21:00 = KST 06:00)

## FR-013 랭킹 조회 API

- `GET /api/trending?platform=&date=&lang=`
- platform 검증(claude|chatgpt|gemini), lang 검증(ko|en|zh), date는 `YYYY-MM-DD`
- 요청일 스냅샷 없으면 최신 스냅샷 폴백, 데이터 없으면 `items: []`
- 응답 항목에 `license`, `taxonomy`, `rank_score`, `summary_status` 포함

## FR-014 주제 탐색 API (v1.0.1)

- `GET /api/topics` — 최근 30일 수집분의 토픽 등장 횟수 상위 50개 `{topic, count}`
- `GET /api/topic-repos?topic=&platform=&lang=&limit=` — 토픽 보유 repo를 `rank_score`→`stars` 순 정렬.
  `platform`은 `all|claude|chatgpt|gemini`, `limit`은 1~50 (기본 10)
- `GET /api/related-topics?topic=` — 공기반 토픽 상위 10개 `{topic, score}`

## FR-015 카드 UI

- 서버 렌더링 Jinja2 + TypeScript 바닐라(`frontend/src/app.ts` → `npm run build` → `src/backend/static/*.js`), Tailwind CDN
- 플랫폼 탭(Claude/ChatGPT/Gemini), 언어 토글(한글/EN/中文), 날짜 선택(`/api/dates`)
- 주제 사이드바(`/api/topics`, 최근 30일 관심순), 주제 상세 시 플랫폼 탭(all/3종) + 관련 주제 칩(`/api/related-topics`)
- 카드: 순위 배지, repo명(GitHub 링크), 라이선스 배지(amber, SPDX 축약), ⭐ star + 오늘 증가량, 언어 태그,
  topics 태그, 3줄 요약(선택 언어), "GitHub에서 보기" 버튼
- 반응형 그리드, 다크모드 기본(`html class="dark"`, 토글 시 localStorage `sr-theme`), Pretendard Variable 폰트
- PWA: `/manifest.json`, `/sw.js`, Web Push 버튼

## FR-016 Web Push 알림

- `POST /api/push/subscribe` — endpoint+keys 저장(upsert)
- `POST /api/push/unsubscribe` — endpoint 삭제
- `GET /api/push/vapid-key` — VAPID 공개키(푸시 미설정 시 빈 문자열)
- 수집 완료 후 `notify_daily_top`: 최신 수집일 플랫폼별 Top1을 전체 구독자에게 발송
- 404/410 응답 시 구독 자동 삭제

## FR-017 수동 수집 API

- `POST /api/admin/refresh`, `Authorization: Bearer <ADMIN_TOKEN>`
- `ADMIN_TOKEN` 미설정 또는 불일치 시 401
- 성공 시 `run_daily_collect` 실행 후 `{"status": "ok"}`

## FR-018 분류 품질 평가 (v1.0.1)

- `src/backend/eval/dataset.json`: 골든 repo 10개 + `expected_label`
- `python -m backend.eval.run_eval`: 각 repo의 README를 가져와 `classify_repo`로 분류,
  `classification_metrics`(accuracy, 레이블별 precision/recall/support, macro 평균) 계산
- 결과를 `docs/experiments/{날짜}-eval-baseline.md`에 기록. `LLM_API_KEY` 없으면 스킵
- `judge_summary`는 채점 전용 — 실패 시 -1.0 센티널로 "채점 실패"를 낮은 점수와 구분

## FR-019 플랫폼별 실패 격리

- `collect_all`: 플랫폼 단위 try/except → 실패 플랫폼 rollback 후 다음 플랫폼 진행
- 파이프라인 노드: 항목 단위 README/요약/분류/검증 실패 → 해당 항목만 폴백·other·unverified로 처리하고 계속
- 캐시(Redis)·체크포인터·푸시 발송 실패도 수집을 막지 않음
