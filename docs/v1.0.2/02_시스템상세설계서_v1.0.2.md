## 3. 데이터 흐름

### 3.1 일일 수집 (스케줄/수동 공용)

1. `collect_all`이 플랫폼 순회 → 플랫폼별 실패는 격리(rollback 후 계속)
2. `collect_platform`이 `run_platform_pipeline`을 호출. 노드 순서:
   - **collect**: `queries.yaml` 쿼리 각각 `search_repositories` 호출 → `full_name` 기준 병합(최대 star 유지) → `RepoRaw` 수집. 쿼리 실패는 errors에 기록하고 계속
   - **dedupe_filter**: `archived`/`fork` 제외 → star 내림차순 상위 10개(`_TOP_K`)만 유지 — 분류·요약·검증 LLM 비용 절약
   - **sanitize**: repo별 `fetch_readme`(동시성 5) → 앞 3000자 + `sanitize_readme`(인젝션 의심 줄 제거)
   - **classify**: `llm_tasks.classify_repo`로 taxonomy 라벨+신뢰도 (동시성 4). LLM 비활성 시 전부 `other`/0.0
   - **summarize**: repo별 3개 언어 요약 (동시성 5). `summary_cache`(content_hash) 히트 시 LLM 호출 생략. 실패 시 description 폴백 + `status='failed'`
   - **verify**: `llm_tasks.verify_summary`로 요약 충실도 검증. 불합격 시 재요약 최대 2회(`_MAX_RETRIES`), 초과 시 `status='unverified'`. 검증 API 실패는 fail-open(True)
   - **rank**: `rank_score = round(log10(stars+1)*20 + (5 if summary ok) + confidence*5, 2)` 계산 후 상위 10개(`_FINAL_TOP_N`) 선정
   - **related**: 스냅샷 내 repo 토픽 공기반으로 관련 주제 산출 (LLM 호출 없음, 주제당 상위 5개)
3. 저장 단계(`collector.collect_platform`):
   - 직전 스냅샷(`collected_date < 오늘` 중 최신)에서 repo→stars 맵 → `stars_today` 계산
   - 같은 `(platform, collected_date)` 스냅샷이 있으면 삭제 후 재생성(멱등)
   - `SnapshotItem`에 taxonomy/taxonomy_confidence/rank_score/summary_status/license 포함 저장
4. `notify_daily_top`: 최신 수집일의 플랫폼별 Top1을 구독자에게 푸시

### 3.2 조회

- `/api/trending`: 요청 날짜 스냅샷 우선, 없으면 해당 플랫폼 최신 스냅샷 폴백
- `/api/topics`: 최근 30일(`TOPIC_WINDOW_DAYS`) 수집분의 GitHub 토픽 등장 횟수 상위 50개
- `/api/topic-repos`: 토픽 보유 repo를 `rank_score`(없으면 -inf) → `stars` 순으로 정렬, 플랫폼 필터(`all` 포함), limit 최대 50
- `/api/related-topics`: 최근 30일 수집분에서 해당 토픽과 공기반된 다른 토픽 상위 10개
- `lang=ko|en|zh` → `SnapshotItem.summary_for(lang)` → 없으면 description 1줄 폴백

## 4. 외부 연동

| 연동 | 방식 | 장애 처리 |
|---|---|---|
| GitHub Search API | `GET /search/repositories` (인증 시 분당 30회) | 403/429/5xx + 네트워크 오류에 지수 backoff, `Retry-After` 헤더 우선. 쿼리 실패는 해당 쿼리만 건너뜀 |
| GitHub README | `GET /repos/{full}/readme?raw=1` (redirect follow), 실패 시 contents API base64 폴백 | 실패 시 빈 문자열 → 요약은 description만으로 진행 |
| LLM 요약 | OpenAI-호환 `POST {LLM_BASE_URL}/chat/completions` (`LLM_MODEL`) | 최대 3회 시도, 최종 실패 시 description 폴백 + `summary_status='failed'` |
| LLM 분류·검증·채점 | 동일 엔드포인트, 모델은 `judge_model`(`LLM_JUDGE_MODEL`, 기본 `LLM_MODEL`) | classify 실패 → `other`/0.0, verify 실패 → fail-open(True), judge 실패 → -1.0 센티널 |
| ~~Redis 캐시~~ | — | v1.0.2에서 제거. 요약 캐시는 `content_hash` DB 조회만 사용 |
| LangSmith | `LANGSMITH_API_KEY`+`LANGSMITH_TRACING=true`일 때만 env 활성화 | 미설정 시 트레이싱 비활성, 실행 후 env 원복 |
| LangGraph 체크포인터 | `CHECKPOINT_PATH` 지정 시 `AsyncSqliteSaver` | 미설정·미설치 시 `MemorySaver` 폴백 |
| Web Push | `pywebpush.webpush` + VAPID | 404/410 응답 시 구독 자동 삭제, 그 외 예외는 로그 후 계속 |

## 5. 설정·보안

- `Settings`(pydantic-settings, frozen): `GITHUB_TOKEN`, `LLM_API_KEY`, `ADMIN_TOKEN` 등 `SecretStr` 처리
- `DATABASE_URL` 스킴 검증: `sqlite:///`, `postgresql://`, `postgres://`, `postgresql+psycopg://`만 허용
- `LLM_BASE_URL`은 https(또는 localhost http)만 허용
- `/api/admin/refresh`는 `Authorization: Bearer <ADMIN_TOKEN>` 또는 `<CRON_SECRET>` 필수, 미설정 시 항상 401. GET·POST 모두 허용(Vercel Cron은 GET 사용)
- `app_env=debug`일 때만 Swagger(`/docs`) 노출
- README 등 저장소 콘텐츠는 신뢰할 수 없는 입력 — `sanitize_readme`가 인젝션 의심 줄을 제거하고, llm_tasks 프롬프트는 콘텐츠를 "데이터"로만 취급하도록 지시
- 라이선스는 GitHub search 응답의 SPDX id를 그대로 사용(추가 API 호출 없음)

## 6. 비기능 요구사항

| 항목 | 기준 |
|---|---|
| Rate limit | GitHub 검색 분당 30회(인증) 준수 — 플랫폼당 쿼리 3회 × 3 플랫폼 = 9회/일. LLM 노드는 동시성 제한(classify/verify 4, summarize 5) + `min_interval` |
| 비용 | content_hash 캐시 + Top10 컷으로 LLM 호출 절약 |
| 격리 | 플랫폼 수집 실패·항목 요약/분류/검증 실패가 전체 작업을 중단시키지 않음 |
| 영속성 | 운영 DB는 Supabase Postgres pooler(`DATABASE_URL`), 로컬은 SQLite |
| 시간대 | 수집일·"오늘" 판정은 Asia/Seoul (`today_kst`) |
| 품질 측정 | `python -m backend.eval.run_eval` → `docs/experiments/` 기록 |
